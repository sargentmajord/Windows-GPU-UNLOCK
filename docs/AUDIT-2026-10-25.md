## Upstream differences checked

- **Windows project** (impacifist/Windows-GPU-UNLOCK): no commits newer than the one this copy started from.
- **Linux project** (Zagitta/gpu-unlock), 22 commits since the version the code was taken from (2026-09-28):
  - GA106 / RTX 3060 support was added as card IDs only; the unlock code itself did not change for it.
  - Suspend/resume re-unlock and kernel claim fixes are Linux-only and do not affect a cold start under UEFI.
  - **Pull request #115** (RTX 3060 `10de:2544`: FWSEC DMEM size 0x980 is not a multiple of 256, unlock fails with -22 and leaves the card stuck
    until a power cycle) is not merged upstream. **Applied in this copy** with regression tests (see CHANGES.md).
- Open upstream issues were read for other problems; the ones that affect users are in TROUBLESHOOTING.md.

## Items found and resolved during the audit

1. Hardware identities of the original author's machines replaced by this machine's (see CHANGES.md); remaining mentions are credits, history and
   NVIDIA's own firmware file names (the code opens them by name).
2. EDID-driver assumption: this firmware has none; the release path now supports that, the test supports it.
3. The test generator and several tests were reading the other author's capture and constants.
4. Broken include path in the stock-selection test; broken documentation links.
5. A speed-selector register value (`0x46425000`) that looked unusual: the code latches the card's first valid starting value and only requires it
   to stay unchanged. It differs between power-ons on this card (`0x46425000` in earlier runs, `0x46421000` in the latest), which is exactly the case the latch handles, so it is accepted by design.
6. FWSEC DMEM alignment bug for this exact card (above).

## Added after the first audit pass (same day)

- The updated diagnostic saved the card's real video BIOS window (`PROM.BIN`, exactly 1 MiB, SHA-256 identical to the fingerprint recorded in all earlier runs).
- **Full-release host test with the real PROM, real PCI config, real handle graph and the card's real NVIDIA display driver image: pass, 9,032 checks**
  (after adapting two scenarios of the test to a flow that has no EDID stage).
- **Real video BIOS parsed with the project's FWSEC parser:** image `0xed00`, IMEM `0xe300`, DMEM `0x980` (not a multiple of 256), 4 signatures (versions `0xf`),
  engine `0x400`, ucode 9. This is exactly the upstream pull request #115 case. The unrounded DMEM is rejected by the Falcon DMA geometry check, the rounded
  size `0xa00` is accepted, and the buffer stays `0xed00`. The fix in this copy is therefore needed and effective for this card's actual data.

## Not yet verified (blocks the unlock stage)

1. ~~The card's real video BIOS image has not been replayed.~~ Done (above).
2. **Write-capable firmware builds are still blocked at compile time** for this profile (deliberately). The unlock program's own tests
   (`test_preflight`, `test_efi_transaction`, `test_experimental`, `test_checks`) need this machine's PROM, the five generated firmware files and a
   cold-state capture in the format those tests read. The firmware files exist and pass their hash checks; the PROM and a converted capture do not exist yet.
3. ~~The five firmware files are named for GA102.~~ Resolved by upstream evidence: the Linux module runs one code path for GA102/GA103/GA104/GA106 (its log prints `family=GA102/GA103/GA104/GA106`), and upstream pull request #115 reports a Zotac RTX 3060 with this card's exact PCI ID `10de:2544` unlocking with the DMEM fix, with the same FWSEC header (4 signatures, versions `0xf`) and the same 12 GB WPR2 layout that this copy's tests compute ([PR #115](https://github.com/Zagitta/gpu-unlock/pull/115)). A different GA106 card (`10de:2504`) is confirmed unlocked in [issue #21](https://github.com/Zagitta/gpu-unlock/issues/21).
4. Behaviour after Windows loads (sleep, long runs) is unverified; reports say sleep loses the unlock.
5. The first run on this card's real hardware of the console-detach test has not happened.

## Verdict

- **Go:** restart once to save `PROM.BIN` (read-only).
- **Conditional go, after PROM.BIN is saved and the full-release test passes on it:** the console-detach test (releases only the RTX 3060's text and graphics
  console drivers, no unlock, then boots Windows), with the user at the PC, Windows first in the boot order and the one-shot boot.
- **Not yet:** any step that writes to the card. Nobody can honestly promise 100%; the remaining gates above are the specific things that must pass first.

## Addendum, later the same day: what happened after the audit, and a second check of this copy

- The gates above were cleared in order and the ladder was run on the reference machine: the unlock program's own tests passed against the real
  capture, video BIOS and firmware files; the write-capable guard was then relaxed in two steps (manual, then automatic; headless stays blocked);
  console-detach, release-only and manual unlock all completed, twice for the unlock. Results: docs/PROFILE-Z790-3060.en.md.
- Items 2, 3 and 5 of "Not yet verified" are therefore closed for this machine. The sleep/restart item (4) is still open, and so is the first
  hardware run of the automatic mode.

     now says what was and was not verified here.
  2. internal-boot/Build.ps1 had been changed to build only the manual pair while Install.ps1 requires both; it builds both again (`-ManualOnly` is opt-in).
  3. docs/PROFILE-Z790-3060.en.md still said write builds were blocked and the GA106 firmware names were unknown.
  4. Several lines of the installer plan had been run together or put out of order by editing mistakes; repaired and re-read in full.
  5. Smaller stale names (a 3090 file name in BUILD, a renamed test in PORTABILITY, broken links after the README move).
- Known label that is deliberately unchanged: the unlock program's log line and build manifests say "hardware untested". That is true for every PC
